## Scope and completeness accounting

ADR 0031 has no separate “Remaining unresolved questions” list. This worksheet
covers its explicit location and future-origin alternatives, the definitions
needed to make its writer policy executable, and the evidence choices for its
specified rename regression. It distinguishes a missing contract from a routine
choice of function or fixture file. It does not reopen requirements already
written in the proposal, and selects no property names, metadata keys, schemas,
origin mappings or defaults.

**ADR-ingester slice is blocked:** ADR 0031 itself must be accepted and B1–B4
must supply a complete declaration/admission contract before production work.
B5 needs the concrete ADR vocabulary and extraction contract before its claim
outputs can be built. B6 is acceptance-evidence work after those choices, not an
independent permission to implement. B7's new origin and B8's listing index are
deferred work and need not precede the report-scoped option-(a) ingester.

The recorded gap remains `GAPS.md:163–173`. No authority or implementation file
is changed by this worksheet.

## B2. Complete vocabulary schema and executable admission constraints

**Missing definition:** `0031:107–121` fixes covered content and canonical
hashing, but does not supply a closed JSON schema, identity/version field domains,
or executable forms for report meaning, artifact applicability and value-shape
constraints (`0031:73–78`). An implementation cannot hash a merely descriptive
list differently at each producer or decide report semantics from a suffix.

| Unselected option | Required implementation | Accepted constraints |
|---|---|---|
| A finite ADR-specific vocabulary with closed entry shapes | Specify exact property strings and each property's report meaning, artifact scope, admitted values and constraint fields. Implement a validator for those closed shapes and publish canonical definition/hash fixtures. | ADR 0023:26–34 preserves exact strings; ADR 0014:169–186 constrains canonical bytes; ADR 0025:80–108 preserves complete recorded provenance. |
| A reusable vocabulary format with a bounded declarative constraint language | Specify every allowed constraint form, evaluation rule, rejection and version rule; implement that interpreter and ADR-specific definitions with the same complete hashing coverage. No arbitrary extension object or inferred normalization can supply a missing rule. | Same exact-property/canonical contracts; ADR 0025:30–33 constrains existing event semantics. |

Both need explicit identity/version domains, duplicate-entry handling, required
versus optional fields, canonical set treatment and rejection fixtures. Runtime
shape validation alone cannot establish that prose asserts only a report. The
accepted-definition trust model belongs to B3. No specific schema or general
constraint language is selected here.

**Blocker:** Yes. **Resolver:** maintainer definition of the closed contract and
reviewable expected acceptance/refusal cases. **Decision:** Unselected.

## B3. Enforcement coverage, external-path designation and definition trust

**Already written, not open:** `0031:73–103` selects the **writer before append**
as the logical enforcement point, forbids omission to evade the external path,
keeps replay independent of policy and acknowledges direct database bypass.
Moving this check solely to an ingester, replay or the standalone verifier is
not a compliant placement alternative. Accepted authority does not identify a
specific Python function where a future policy must live.

**Missing contract:** how the writer recognizes the external-content path even
when a declaration is missing, and how it establishes that a supplied definition
has admissible report meaning rather than a valid hash over false semantics.
`GAPS.md:164–167` explicitly says `source_class` alone supplies no such boundary.

| Unselected option | Required implementation | Accepted constraints |
|---|---|---|
| A writer-owned external-ingestion entry point with controlled producer routing | Specify which producers must use it and how unrestricted submission cannot serve as an alternative for those producers. Enforce declaration and definition validation under the writer boundary before either mention or observation mutation. | ADR 0030:33–59,64–79 governs sole writer and semantic submission; ADR 0023:67–110 governs bootstrap and retries. |
| A writer-owned producer/policy classification applied to all submission routes | Specify the trusted binding that identifies external submissions without trusting a removable caller declaration. Check all applicable append routes and reject missing metadata before mutation. | Same writer/retry constraints; ADR 0025:174–184 does not let replay success certify writer policy. |

For definition trust, unselected compatible mechanisms include a reviewed set of
allowed complete definitions addressed by hash, or a closed report-template
format whose admitted meanings and scope constraints the writer validates.
The former needs controlled definition admission/versioning; the latter needs
the executable contract in B2. A hash proves bytes, not report meaning or faithful
extraction. Neither mechanism is a global property-identity registry. Choosing
only the source file/function is routine implementation work once coverage and
trust are specified; it is not by itself a new authority gap.

**Bounded enforcement claim:** the writer cannot detect external content from
arbitrary submitted text. The maintainer must name which caller/producer facts
are trusted: for example, a controlled ingester route and its configured producer
identity, or a writer-owned binding of a producer to external-ingestion policy.
Caller-supplied `source_class`, `actor_id` or a removable vocabulary declaration
are not automatically authenticated classification facts. ADR 0030's sole-writer
exclusion does not itself authenticate an upstream producer. These are three
separate claims:

| Claim | Boundary and evidence required |
|---|---|
| Authorized-route enforcement | Given the explicitly trusted routing/producer facts, every submission through the covered routes is checked before append; omitting the declaration or switching a route available to that producer cannot evade the check inside that boundary. Enumerate covered routes and trusted facts and test attempted omissions/re-routing. No assertion that arbitrary submitted text can be classified is implied. |
| Faithful extraction | Admission of a reviewed vocabulary/hash does not prove that the extractor read artifact A at revision R correctly. Deterministic extraction and input/output fixtures provide separate evidence; producer attribution alone is not that proof. |
| Direct-database bypass | A process writing database rows outside the authorized writer boundary bypasses this admission policy. Ordinary integrity/replay success is not evidence that the policy ran (`0031:99–103`). |

**B3/B4 retry cases under vocabulary policy change:** preserving semantic
metadata alone does not settle admissibility of an uncommitted submission.

| Case | Required acceptance evidence or unresolved ruling |
|---|---|
| Equivalent committed retry after its vocabulary leaves admission policy | Under `decisions/0030-sole-writer-and-positional-fields.md:92–110`, return the complete original committed pair unchanged. Demonstrate that removal does not turn equivalent reuse into new admission, substitute a vocabulary version, remint IDs or sample new positions. Conflicting semantic reuse still refuses. |
| Uncommitted submission retained under a vocabulary that has since been removed | **Maintainer ruling required:** continued admission of retained submissions versus refusal under current policy. ADR 0030:87–90 preserves semantics/IDs but supplies no vocabulary-admission grandfathering rule. State how policy epoch or retained-submission evidence is established if continued admission is selected. Test the selected behavior without silently rewriting metadata. |
| Committed mention plus uncommitted observation when policy changes between them | The committed mention remains valid (`decisions/0023-stage-two-contract.md:107–110`). Its equivalent retry returns its original pair. **Maintainer ruling required** for admission of the still-uncommitted observation under the removed vocabulary, including whether a retained bootstrap unit has any admission guarantee. The two appends are separate; no atomic policy guarantee follows from preserved declaration bytes. |

These uncommitted-admission choices block the slice's policy-change/recovery
contract. Neither continued admission nor refusal is selected here.

**Blocker:** Yes, for enforceable coverage and definition admission. **Resolver:**
maintainer policy/trust ruling plus bypass, missing-declaration and no-mutation
tests. **Decision:** Unselected.

## B4. Exact definition preservation and immutable-version consistency

**Missing contract:** `0031:123–135,147–150` requires preservation of the exact
definition addressed by identity/version/hash and refusal of reassignment, but
does not select its durable location or retrieval/retention contract. Mutable
URLs alone are explicitly insufficient. Replay must not acquire a new dependency
on definition availability (`0031:93–103`).

**Canonical bytes versus source formatting:** the hash input is the complete
definition serialized as canonical JSON (`0031:107–121`), not the original JSON
file's whitespace, indentation or object-key order. Preserve the canonical
definition bytes used for the hash. **Maintainer question:** must the original
source-file bytes also be retained for extraction/review provenance, and where
and for how long? Retaining canonical bytes alone and retaining canonical plus
original source bytes are unselected options. A formatting-only source-file
change does not change covered definition content and does not by itself require
a new vocabulary version. Changes to covered semantics do require a new
version/hash under `0031:123–130`.

| Definition fixture | Expected evidence under the proposed hash discipline |
|---|---|
| Same parsed definition, different indentation/whitespace | Identical canonical definition bytes and hash, regardless of whether original source-byte retention is selected. |
| Same definition, different object-key insertion/source order | Identical canonical bytes/hash; set-valued collections still use the explicitly defined canonical set treatment, while semantic sequences retain order. |
| Changed covered property, scope, value constraint or covered label | Changed canonical bytes/hash, with a new vocabulary version for new admission; old declarations/committed retries stay unchanged. |

These are fixture requirements after B2 defines a concrete schema, not an
implementation of the proposed vocabulary format.

| Unselected option | Required implementation | Accepted constraints |
|---|---|---|
| Include complete definition content in a compatible event provenance location | Decide exact content/layout through B1; verify the declared hash before append; retain original definition on retries. Reconstruct the identity/version-to-hash consistency lookup from events. | ADR 0023:78–110; ADR 0030:64–100; ADR 0025:30–33 and full provenance coverage. |
| Retain content-addressed definitions separately while each event commits the declaration | Specify durable canonical-definition-byte storage, any separately selected original-source-byte retention, backup/retrieval and behavior when ingestion review cannot retrieve a definition. Implement verification and preservation before dependent acceptance; reconstruct the consistency lookup from per-event declarations. Historical replay still needs no mutable policy lookup. | ADR 0030:33–59,85–100 constrains acceptance/crash/retry boundaries; ADR 0025:174–184 distinguishes integrity from semantic policy. |

In either option, serialize consistency checks with the writer so a competing
submission cannot reassign an identity/version between validation and append.
Physical indexing is an implementation detail; making the preserved definition
authoritative for historical replay would contradict the proposal. No new Layer A
definition event type is authorized by naming this requirement.

**Blocker:** Yes, before claims of reproducible ingestion policy. **Resolver:**
maintainer durability/location contract and recovery/reassignment evidence.
**Decision:** Unselected.

## B5. Concrete ADR vocabulary, extraction and recorded scope

**Missing slice definition:** `0031:30–55,73–78,161–179` describes report meaning
and rename boundaries without supplying the actual ADR property vocabulary,
extraction/value rules or an artifact/revision scope representation. It does not
select a repository importer CLI, timestamp-import policy or retry manifest.

| Unselected option | Required implementation | Accepted constraints |
|---|---|---|
| A narrow ADR metadata vocabulary and deterministic extractor | Define exactly which observed fields are admitted, their value shapes, artifact/revision provenance and handling of malformed or repeated fields. Missing status produces no fabricated status claim. Specify retained submissions and associations across revisions. | ADR 0006:46–59 preserves timestamp spelling; ADR 0019:80–92 and ADR 0023:26–110 preserve identities, fresh candidates and retries; ADR 0024:27–66 forbids a recency head. |
| A broader explicit artifact-statement vocabulary with ADR extraction as one producer | Define the additional report types/scopes and extraction validation before admitting them, plus the same provenance and retry contract. A broad vocabulary cannot authorize embedded world assertions or identity association from ADR numbers. | Same contracts; ADR 0026:17–29 prevents retrieval from becoming evidence; ADR 0025:30–39 supplies no new handlers. |

Define the slice's mapping from each imported path/revision to recorded mentions
and subject scope. Reusing an explicitly recorded mention for a later revision is
permitted by ADR 0023:60–74 only within its stated scope; creating a genuinely new
mention requires its own scoped subject. Either representation must make report
revision explicit, preserve earlier candidates and use a separate subject for
the renamed path. No generic “same ADR number means same subject” option exists.
The choice must state what future “appropriate existing belief” means rather than
inventing a cross-subject association.

The draft fixes public-only ingestion (`0031:184–194`), but not a particular
deployment's public-corpus inventory or admission evidence. A deployment must
identify its actual public inputs; a reviewed public input allowlist or explicit
operator corpus declaration are evidence-policy possibilities, neither already
decided here. Locally readable is not the public test. This does not ratify any
private-corpus, erasure or user-entitlement mechanism.

**Blocker:** Yes, for the concrete ADR-ingester outputs; public-input evidence is
a deployment readiness requirement. Routine parser packaging and file names need
no new authority ruling once the extraction contract is explicit.
**Resolver:** maintainer slice/vocabulary contract and its extraction fixtures.
**Decision:** Unselected.

## B8. Future listing index and protected deployment

`0031:196–207` permits an inventoried derived mention-text copy in the proposal
but explicitly leaves its schema/API, search/ranking/embeddings and usage mechanics
to separate work. A replay-derived persisted index would need schema, rebuild,
publication/staleness and complete copy inventory; an on-demand listing would
need an explicit read contract and freshness disclosure. Neither is supplied by
ADR 0031, and neither may become sole durable facts, an identity matcher or a
candidate head.

Accepted constraints: ADR 0014:191–200,221–245 governs view/freshness/publication;
ADR 0024:27–52 forbids head selection; ADR 0026:17–37 forbids usage evidence.
Proposed ADRs 0027/0028 are not accepted privacy authority. Public-only policy
remains until the separately stated acceptance, implementation and assurance
requirements are met (`0031:184–194`). A private deployment needs those later
contracts and evidence, not an inferred exception from local access.

**Blocker:** No for a public option-(a) ingester with no index; yes for the deferred
index/protected deployment it describes. **Resolver:** separate maintainer
contracts and applicable assurance evidence. **Decision:** Unselected; out of
scope for this queue.
